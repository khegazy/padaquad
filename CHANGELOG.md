# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [2.0.0] - 2026-11-25

This release removes the solver's hidden warm-start state and the memory benchmark that ran before every `integrate` call without `max_batch` (it took longer than many integrals). A call reuses an earlier call's mesh and batch size only when they are passed to it (`result, state = solver.integrate(...)`, then `state=state`), so no call can change what another call reuses, and every call says which interval it integrates. See "Reusing the mesh and batch size" in the README and the user guide.

With `take_gradient=False`, every pass now evaluates all its waiting subintervals before any is accepted or split, so the mesh no longer depends on the batch size. `conserve_memory` is replaced by `trade_speed_for_memory`, `evaluation_buffer` and `record_evaluations`, which choose between speed and memory without changing the calls of `f`, the mesh or the integral; by default a pass's values are held on the device once. Accepted subintervals are judged again as the integral changes (`enforce_convergence`), and `error_on_nonfinite` is merged into `runtime_checks`. See "Memory efficiency and speed options" and "Renamed and removed arguments" in the user guide.

### Removed

- **`solver.atol_assert` and `solver.rtol_assert`**, the looser tolerances of the per-pass order checks of the nodes and the mesh, which are gone (the mesh and the nodes are in order by construction; see Changed). No check read `rtol_assert`.
- **`IntegrationResult.mesh_optimal`** (and the unreleased `IntegrationResult.max_batch`): they are the state's `mesh` and `max_batch`, returned beside the result, `result, state = solver.integrate(...)`. Replace `result.mesh_optimal` by `state.mesh`, and `result = integrate(...)` by `result, state = integrate(...)` (or `result, _ = ...`).
- **`same_f`, `solver.mesh_previous` and `solver.previous_max_batch`.** The solver no longer stores the mesh and batch size of its last call. Passing `same_f=` raises `TypeError`. To migrate, keep the state the earlier call returned and pass it: replace `result = solver.integrate(f, same_f=True, ...)` by `result, state = solver.integrate(f, state=state, ...)`, where `state` is what the call to start from returned. On the first iteration pass the bounds instead (`state=None`).
- **`get_max_batch(default_max_batch=...)`.** It returned the value passed in, lowered to the out-of-memory cap, and existed only for the solver's own use; passing it raises `TypeError`. Pass a known batch size to `integrate(max_batch=...)` directly; `get_max_batch` now only measures (`f=`, `t=`) or estimates from what the solver knows.
- **The constructor's `mesh_init` and `mesh_final`.** Passing them raises `TypeError`. Pass the bounds, or a mesh, to every `integrate` call.
- **`MethodClass.clone`, `to_dtype` and `to_device`** (and `_Tableau.to_dtype`/`to_device`). They changed a method in place; replace `method.clone()` followed by `to_device(device)` and `to_dtype(dtype)` by `method.to(device, dtype)`, which returns a converted copy and leaves `method` unchanged (see Changed). A subclass of `MethodClass` now implements `_map_tensors(fn)` (a shallow copy with `fn` applied to each tensor) instead of `to_dtype` and `to_device`. `_Tableau` is frozen: its fields cannot be reassigned.

### Added

- **`integrate` returns a pair `result, state`, and takes `state=`.** The `IntegrationState` holds the call's optimal mesh (`state.mesh`), its batch size (`state.max_batch`, the most points per call of `f` known to fit) and whether that may still grow (`state.max_batch_converged`). Pass `state=state` to start the next call from both. It is a frozen dataclass; `dataclasses.asdict` gives a dictionary that `torch.load` reads with `weights_only=True`. Passing both `mesh=` and `state=` raises `ValueError`; a `max_batch=` given with a state replaces its batch size.
- **`integrate(parameters=...)`** and **`BackwardOutOfMemoryError`.** With `take_gradient=True`, an out-of-memory error in a backward pass (or in `loss_fxn`) now restarts the integral with smaller batches, after putting back the gradients the call added (found by walking each batch's autograd graph). `parameters=` (tensors or an optimizer) is needed only when the integrand uses a custom autograd function, which can hide parameters from that walk; without it, and with a post-accumulate-grad hook or several `torch.distributed` processes, the call raises `BackwardOutOfMemoryError` (a `torch.OutOfMemoryError`) whose `state` is the state to call again with after resetting the gradients.
- **`solver.get_max_batch(f=f, t=t, take_gradient=..., f_args=...)`** runs the memory benchmark for `f`, in `t`'s dtype, and returns the batch size to pass as `max_batch`, so it can be measured once before any integral. It is the only caller of the memory benchmark, and its start warning is shorter. Its first call of `f`, on one point, is checked like every call of `f` in `integrate` (shape [N, D], one row per point), and an out-of-memory error there is raised as `torch.OutOfMemoryError`. Without `f`, `get_max_batch()` returns the constructor's `max_batch`, else the last measurement's value. `get_max_batch(evaluation_buffer=...)` keeps twice that many bytes free (the values waiting for their quadrature calculation with `trade_speed_for_memory=True`, and their copy when they are joined), with or without `f`; `integrate` itself does not reserve it.
- **Bounds inside a given mesh cut it, and bounds outside it extend it.** `integrate(f, mesh=m, mesh_final=c)` integrates up to `c`, starting from the points of `m` before `c`, and from `m` with `c` appended when `c` lies beyond `m`; previously the bounds had to equal the mesh's ends.
- **The example "The gradient as extra outputs"** (`examples/gradient_as_output.py`): `f` returns its integrand and the gradient of the integrand with respect to two parameters (`torch.func.grad`), so one call gives the integral and its gradient without an autograd graph; a callable `error_norm` chooses whether the integrand, the gradient or both decide a split (with `dopri5` at rtol 1e-6, judging on the integrand alone leaves the gradient's error 60 times larger). The gallery shows matplotlib figures; matplotlib joins the `dev` and `docs` extras.
- **`integrate(record_evaluations=False)`** deletes the integrand values and tracked variables as soon as their subintervals are integrated, so they are never moved to `result_device` or kept: `result.y` and `result.tracked_variables` are `None` (also in the results `loss_fxn` receives), and the state's mesh is built with `merge_rule="power_law"`, because `"predicted"` reads the values (a warning on the first call says so when the solver's `merge_rule` is `"predicted"`). The mesh and the integral do not change. For the network with 100,000 outputs above, the host's peak memory falls from 48.9 GB to 2.1 GB and the time from 18.2 s to 4.7 s (4.6 s with `trade_speed_for_memory=True`).
- **`integrate(build_state_mesh=False)`** skips building the state's mesh (the optimal mesh) after the integration and returns `state.mesh = None`, for calls whose mesh no later call starts from. The default, `True`, builds it as before. A later call given such a state keeps its batch size but needs both bounds (without them the `ValueError` names the switch) and starts from a fresh mesh; the restart after a backward out-of-memory error keeps the switch. On an A100 node (gk21, float64, 11 and 13 subintervals, the second with 1,000 outputs) a call falls from 4.5 to 3.0 ms and from 9.1 to 7.1 ms with a GPU solver, and from 2.8 to 1.4 ms and from 6.0 to 4.2 ms with a CPU solver. Reusing the loop's final mesh instead was rejected: it is never merged, and 20 calls from it evaluated the integrand at 1.9 to 2.4 times as many points as from the optimal mesh.
- **`integrate(enforce_convergence=...)`** controls the re-check of accepted subintervals: each batch, every accepted subinterval is judged again, from its stored error estimate, against the same integral as the subintervals just evaluated, and split if it fails (with a fixed `error_integral_reference`, only once that reference is dropped; see Changed). None (the default) means `not take_gradient`, so without a fixed reference the default behavior is unchanged; `False` turns the re-check off with `take_gradient=False`; `True` with `take_gradient=True` raises `ValueError`, because a batch's gradient is already backpropagated when it is accepted and splitting it again would count it twice. When a fixed reference is dropped and accepted subintervals fail, an INFO log line reports how many fail and how many of them are split.

### Changed

- **`error_ratios` no longer requires grad.** With `take_gradient=False` and an integrand that depends on parameters, or a bound that requires grad, `result.error_ratios` and the `error_ratios` of each per-batch result `loss_fxn` receives had `requires_grad=True`: the rounding floor, the running integral and, in cumulative mode, the running sums carried the autograd graph into them, and with it the arrays its nodes saved for a backward pass that error control never needs. Error control now reads detached values, so `error_ratios` holds no graph; its values, the integral and its gradients are unchanged, bit for bit.
- **Solvers share their converted method, built once per process.** Each solver deep-copied its method and copied its three tables to the device when it was built (most of the 0.32 ms that building a solver took on an A100; it now takes 0.08 ms), and with `result_device` on another device moved the tables there and back on every call (six host waits on a GPU). `MethodClass.to(device, dtype)` now returns a copy of the method on that device in that dtype, built on first use and kept while the method lives (the registry entries for the life of the process), so every solver of the same method, device and dtype uses the same object, and `result_device` swaps one object for another. A method's tensors must not be modified in place, since the change would reach every solver that uses it; the registries are never changed. Results are unchanged, bit for bit.
- **The state's mesh costs less to build.** The merge prediction no longer checks that every recorded node sits at its method's node fraction, which is true by construction since the state's mesh is built from the final mesh, and it multiplies the stored integrand values as they are instead of copying them twice per chunk (a strided record, such as a transposed output of `f`, is still copied once, so the prediction does not depend on how the values are laid out) (the merge weight vectors have one entry per node, 0 at a repeated node fraction). On an A100 node (gk21, float64, a new solver per call) building the state's mesh falls from 1.78 to 1.66 ms (11 subintervals), from 2.53 to 2.14 ms (13 subintervals, 1,000 outputs) and from 9.0 to 8.2 ms (13,737 subintervals) with a GPU solver and the record on the CPU, and from 1.92 to 1.73, 2.32 to 2.16 and 9.0 to 7.7 ms with a CPU solver. Results are unchanged, bit for bit; for a method of your own that repeats a node fraction, the merge prediction can change at rounding level.
- **Less error-control work in every pass.** Absolute mode (the default) no longer merges each pass into the record's order to build running sums that only cumulative mode reads, and cumulative mode sums once per pass instead of twice; the pair error ratio of neighbouring subintervals is computed only where the state's mesh merges them, not for every pass, re-check and final check; the re-check of accepted subintervals reads the device once per pass instead of twice; and with the norm-family `error_norm` options the record keeps each subinterval's reduced error and rounding floor as its pass computed them, so the re-check and the final `converged` check compare stored numbers with the tolerance instead of reducing the record's `[N, D]` error and contribution arrays again. On an A100 (gk21, float64, `atol=1e-8`, `rtol=0`, a new solver per call, median of 21 calls), `sin(1/(t + 0.001))` on [0, 1] (77 subintervals, 14 passes) falls from 40.0 to 32.5 ms (103 to 90 host waits, 2,823 to 2,331 GPU launches with `error_norm="max"`), with `"failure_fraction"` from 42.0 to 33.8 ms, in cumulative mode from 40.3 to 36.1 ms, with 1,000 outputs from 10.9 to 8.3 ms, and `sin(2e5 t)` (13,737 subintervals) from 37.2 to 31.4 ms; on the CPU (16 threads) from 13.5 to 11.6, 14.3 to 11.9, 13.6 to 12.9, 6.1 to 5.7 and 26.2 to 23.6 ms. One re-check of 2,000 accepted subintervals with 100,000 outputs (`"2"`) falls from 24.8 ms and 6.0 GiB of temporary GPU memory to 0.7 ms and none. Results are unchanged, bit for bit, on 2,240 integrations on a CPU and an A100 that cover every `error_norm`, both modes and up to 10,000 outputs. The one exception in principle: with `"2"`, `"rms"` or a callable norm and many outputs, the reduction of one subinterval's errors can differ in its last bit between the array of its pass and the array of the whole record (on the A100 for up to 12 % of the recorded subintervals with 1,000 outputs, by at most 3e-16 relative); the re-check and the final check now use the value its pass computed, so a decision within that much of the tolerance can differ from the previous version (none did in 48 test integrations), and the re-check, the final check and the acceptance can no longer disagree through rounding. A callable `error_norm` must therefore reduce each row on its own.
- **Fewer waits for the GPU in every pass.** Each pass of the integration loop read device values on the host about 46 times on a GPU (each read makes the host wait until the GPU has finished its queue): boolean masks select the accepted subintervals, the waiting subintervals and the values to keep, and the order of the mesh was checked. The mesh update now reads the number of accepted subintervals once and indexes every field with integer positions, the loop finds the waiting subintervals with one read, and the per-pass order checks of the mesh and the nodes are gone (see `runtime_checks` below). On an A100 (`sin(1/(t + 0.001))` on [0, 1], gk21, float64, `atol=1e-8`, 14 passes) a call falls from 57 to 52 ms (648 to 412 host waits, 3,739 to 3,234 GPU launches), and with `take_gradient=True` and `max_batch=230` from 63 to 53 ms (738 to 422 waits). Results are unchanged, bit for bit.
- **The record of accepted subintervals is kept without a dictionary of the mesh, and put in mesh order once.** After every mesh update the whole mesh was copied to the host and turned into a Python dictionary from each mesh point to its index, each recorded subinterval was looked up in it by its left mesh point, and every field of the record, the integrand values included, was merged into a new array on every pass. Each recorded subinterval now carries the integer index of its left mesh point, kept current by one gather after each mesh update; each pass's accepted subintervals are appended, and the record is put in mesh order once, after the loop (a record of one pass, already in order, is not copied). The nodes, widths, error ratios and loss of accepted subintervals now wait on the solver's device until the end of the call instead of moving to `result_device` on every pass (about 184 bytes per subinterval for `gk21` in float64); the values still move on every pass, so the GPU holds no accepted values with `result_device="cpu"`. On an A100 (gk21, float64, `atol=1e-8`, `rtol=0`, `max_batch=1e6`), `sin(2e5 t)` on [0, 1] (13,737 subintervals, 13 passes) falls from a median of 123 ms (minimum 89, maximum 145: the time alternated between two speeds) to 37 ms (35 to 40), and on the CPU from 105 to 30 ms; each call ran about 100 garbage collections of Python objects (one of them of the oldest generation, most of the time), now none. `sin(1/(t + 0.001))` (77 subintervals, 14 passes) falls from 48 to 37 ms on the A100 (412 to 103 host waits) and from 16.2 to 13.5 ms on the CPU. With the record on the GPU (`result_device=None`), recording a pass no longer allocates the record's values again (the GPU's peak for 4096 outputs and 1,500 subintervals fell from 2.51 to 2.30 times the recorded values); the end of the call still holds the values twice while `result.y` is built, and the final ordering, when the record is not in order, holds them twice as well. A path through the same point twice no longer maps two mesh points to one key. This replaces the mesh-position dictionary of the entry "Record ordering is now by mesh position" below. Results are unchanged, bit for bit (1,720 integrations on a CPU and an A100).
- **Less fixed cost per `integrate` call.** Besides the shared methods and the float tolerances below, the default `y0` is filled on the device, the starting mesh's trackers are built without a copy from the host, a fresh mesh is checked once instead of twice, the split statistics and the convergence check are read from the device at once, and a mesh given without bounds (`integrate(f, state=state)`) is no longer cut to its own ends. On an A100 (`exp(-t) sin(40 t)` on [0, 1], gk21, float64, 11 subintervals) a one-shot `padaquad.integrate` call falls from 6.7 to 6.1 ms (61 to 41 host waits) and a call with `state=` from 5.8 to 5.3 ms (53 to 39); on the CPU from 3.32 to 3.15 ms and from 2.60 to 2.53 ms. Results are unchanged, bit for bit.
- **`solver.atol` and `solver.rtol` are Python floats**, not tensors on the solver's device (`float(solver.atol)` still works; `solver.atol.item()` does not). Each was copied to the device when the solver was built and moved to `result_device` in the two error checks of the optimal mesh (four host waits per call on a GPU with `result_device="cpu"`). A tolerance that is negative, NaN or infinite now raises `ValueError` (it was accepted, and made every subinterval pass). So does a tolerance that is not one number, such as a list or tensor with one value per output component, which `error_norm="failure_fraction"` used to accept as per-component tolerances although the documentation always said a float; a string that `float()` reads, such as `"1e-5"`, which raised `TypeError`, is now accepted. Results are unchanged, bit for bit, when the integrand's values have the solver's dtype, except after a dtype switch: a float64 solver that a call with float32 bounds or mesh switched to float32 kept its tolerances rounded to float32 when a later call switched it back to float64, and now uses them as given (the error ratios of those later calls change by about 1e-8, relative, which can change a decision to accept or split). When an integrand returns float64 values to a float32 solver, the tolerances are likewise used as given instead of rounded to float32 (a relative change of about 1e-8 in the tolerance).
- **The Gauss-Kronrod methods evaluate the integrand only at their 2n + 1 nodes per subinterval**, not at two more points of weight zero at the subinterval's ends: `gk7`, `gk15`, `gk21` (the default) and `gk31` call `f` at 7, 15, 21 and 31 points per subinterval instead of 9, 17, 23 and 33 (8.7 % fewer points for `gk21`, 22 % for `gk7`), and hold that much less memory for a pass's values. The solver takes each subinterval's width and place from the mesh, so a method's nodes no longer have to include the ends (`MethodClass` accepts node fractions anywhere in [0, 1]). `result.nodes`, `result.y` and `result.tracked_variables` list every evaluated point once: for a Gauss-Kronrod method `N C` rows and no mesh point (they no longer contain `mesh_init`, `mesh_final` or any other mesh point); for the other methods `N (C - 1) + 1` rows as before. The per-batch results `loss_fxn` receives have `C` rows per subinterval as before (21 for `gk21`). Integrals and error estimates of the Gauss-Kronrod methods change at rounding level, because the weighted sum has two fewer terms of zero (see the snapshot data); the state's mesh can differ by a few subintervals, because the merge prediction interpolates through the evaluated nodes only. The gradient with respect to a bound that requires grad changes at rounding level for every method (the width's contribution is added separately from the nodes').
- **`dopri5` evaluates the integrand at 5 points per subinterval instead of 7.** Its tableau's stage at fraction 1/5 has weight zero in both weight sets, and its two stages at fraction 1 evaluate the same point; as a quadrature method it now has the nodes 0, 3/10, 4/5, 8/9, 1, with the two stages' weights at 1 added (error weight 71/6300 = 11/84 - 649/6300 - 1/60). 28.6 % fewer points; its integrals and error estimates change at rounding level (the weighted sums have other terms), and `result.nodes`/`result.y` lose two rows per subinterval.
- **`error_on_nonfinite` is merged into `runtime_checks`** (constructor and `integrate`, default `True`). With `True`, a NaN or Inf value of the integrand raises `ValueError` naming its points, as `error_on_nonfinite=True` did, and PadaQuad's own bookkeeping is checked (that the accepted subintervals cover the final mesh once, one check at the end of the call); the mesh and the nodes are no longer checked on every pass, since they are in order by construction. With `False`, all these checks are skipped: subintervals where the integrand is NaN or Inf are accepted and the value reaches the result, as with `error_on_nonfinite=False`, and no check allocates a temporary array as large as a call's output (the finite check of a call of 35,328 points with 100,000 outputs ran out of memory on a 40 GB A100 after the call itself fit). The loop still ends on non-finite values either way: their subintervals are accepted, not split. `error_on_nonfinite=` raises `TypeError`: pass `runtime_checks=` instead.
- **The number of segments of a fresh starting mesh is the exact integer square root of `N_init_steps`** (`math.isqrt`). It was computed with PyTorch's float32 square root, which on an AVX2 CPU with torch 2.8 rounds up just below a perfect square from `N_init_steps` = 9,443,328 = 3073² − 1 on (3,368 values up to 3·10⁷ gave one segment more). Starting meshes for smaller `N_init_steps` (the default is 13) are unchanged; a float `N_init_steps` such as `1e4` is still accepted.
- **`conserve_memory` is replaced by `trade_speed_for_memory` and `evaluation_buffer`, and every pass is judged whole.** With `take_gradient=False`, every pass now evaluates all waiting subintervals, in calls of at most `max_batch` points, before any is accepted or split, whatever the options. `conserve_memory=True` evaluated one batch per pass and judged it alone against the running integral of the batches before it, so the mesh depended on `max_batch`, which PadaQuad itself sets from free memory: `exp(30t)` on [0, 1] (gk7, rtol 1e-8, atol 1e-14, float64, with float64 as torch's default dtype for the random starting mesh) needed 1126 integrand points at `max_batch=18` (694 at 50, 1162 at 5) instead of 298. By default a pass's integrand values stay on the solver's device until all its subintervals are evaluated, and their contributions and error estimates are computed at once; only the accepted subintervals' values then move to `result_device`. With `trade_speed_for_memory=True` the values of whole subintervals are integrated as soon as `evaluation_buffer` bytes of them wait (after every call of `f` without it) and move to `result_device` right away. The points evaluated, the mesh and the integral are the same, bit for bit, with every setting (checked on 1,460 integrations on a CPU and on a GPU), and so are the calls of `f` unless the batch size is still growing toward an out-of-memory error (the memory the option frees can let it grow further). Measured on an A100 for a network with 100,000 outputs (float32, gk21, 1,904 subintervals in 25 calls of 4,600 points, `result_device="cpu"`; `examples/speed_test/trade_speed_for_memory.py` at commit 2e59d54), the GPU's peak memory is 7.8 GB with the option and 23.9 GB without (the contributions and error estimates of every subinterval stay on the device), at 20.4 s against 18.2 s, with the same host memory. Integrating after every call costs about 0.1 ms per call of `f` on a CPU and 0.2 ms on an A100 (75 calls of 46 points); a buffer removes that cost. `integrate` raises `ValueError` for `trade_speed_for_memory=True` with `take_gradient=True` (nothing to trade) and for an `evaluation_buffer` given without it or not an int of at least 1, and logs warnings on the first call of a series (no `state`): without a buffer, and with an integrand whose output requires grad (the warning recommends returning the gradient as extra outputs of `f`, see Added). `conserve_memory=` raises `TypeError`: pass `trade_speed_for_memory=` instead.
- **The values kept on the host (`result_device="cpu"`) peak at about twice their size, down from three times.** Adding each pass's accepted values to the record cloned the whole record first, building `result.y` flattened the values and then joined them (two copies), and the final sort copied the record although it is always in order. The record is now read without a clone, `result.y` is written in one copy, and a record in order is not sorted. For 29 GB of values (a 512 x 512 field, 1,349 gk21 subintervals) the host's peak fell from 3.14 to 2.18 times the values (measured on a 40 GB A100 node). The results are unchanged, bit for bit.
- **The quadrature calculation no longer needs a temporary copy of the integrand values.** The weighted sum over the nodes formed the products of weights and values for every subinterval at once, an array as large as the values (once for the contributions and once for the error estimates). On a 40 GB A100 that array ran out of memory after `f` had returned, where the batch size cannot be reduced and the integration stops. The products are now formed for at most 128 MiB of subintervals at a time, with the same results bit for bit (each subinterval's sum depends only on its own values).
- **By default, a pass's integrand values are held on the device once.** Each call's values were kept in a list and joined into one array when the pass was integrated, and the accepted subintervals' values were then selected by indexing, even when every subinterval was accepted; both made a second copy, so the device briefly held about twice the pass's values. The last pass's values also stayed referenced into the next pass and the sorting of the record. Now each call writes its values into one array allocated for the pass (the number of subintervals is known before the first call, since none is split during a pass), the quadrature is calculated from its rows, and the accepted rows are moved to the front of the same array. For 4096 outputs and a pass of 1000 gk21 subintervals of which 500 are split, the GPU's peak falls from 2.43 to 1.55 times the pass's values (the rest is the contributions and error estimates of every subinterval); for 100,000 outputs and 1,000 gk21 subintervals, the host's peak with `trade_speed_for_memory=True` falls from 68.5 GB to 51.4 GB. When one call of `f` covers a pass, its output is kept as the pass's values without a copy, and the accepted rows are copied from it rather than moved within it, since `f` may still hold its output. This also holds with `record_evaluations=False`. On a 40 GB A100, an integrand with 262,144 float32 outputs (1,349 subintervals) that ran out of memory at every `max_batch` without `trade_speed_for_memory` now completes at `max_batch` 1,000 and 2,000. An integrand output that requires grad keeps the former path. The results are unchanged, bit for bit. If the pass's array does not fit, `integrate` raises `torch.OutOfMemoryError` naming the pass's size and the remedies (`trade_speed_for_memory=True`, or `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` when PyTorch reports much memory reserved but unallocated); the user guide's section "Out of memory with many outputs" explains both.
- **`interpolatory3_variable`'s weights are laid out per subinterval** (stacked along the last axis instead of transposed). On a GPU the sum over a subinterval's nodes depended on how many subintervals one call held; results on a GPU change in the last bit (at most 2e-7 relative in float32 over 1,640 integrations), results on a CPU do not change.
- **With `take_gradient=False`, a fixed `error_integral_reference` is dropped once every subinterval is accepted.** The loop judged every subinterval against the reference, but `converged` judges them against the final integral, so a reference larger than the integral left `converged=False` (for `sin(2πt)` on [0, 1] with reference 1.0 and `bosh3`, atol 1e-9, rtol 1e-6, `max_batch=16`, seed 0: 113 subintervals, integral -2.4e-7). Now every accepted subinterval is judged, from its stored error estimate, against the integral of all of them at that moment; the failures are split, and the integration continues against the running integral until it converges, or until `max_adaptive_splits` or a non-finite value stops the refinement (the same run: 1045 subintervals, integral -8.4e-10, `converged=True`); no subinterval is evaluated twice. Default results change only for a call with `take_gradient=False` and a fixed reference in which such a subinterval exists; pass `enforce_convergence=False` for the previous result.
- **Every point at which `integrate` calls the integrand belongs to the integral.** `integrate` no longer calls `f` on one point to check the shape of its output (on every call, also with `max_batch` or a state), nor, without `max_batch` or a state, on 10, 100 and 1,000 copies of one point to see that it runs; both results were thrown away. A cold gk21 call on the default starting mesh evaluated 342 points for the 231 of its first pass (4 calls of `f`); it now evaluates 231 in one call, and a call from a state or with `max_batch` one point and one call fewer. The output is now checked on every call of `f` during the integration (Fixed); a wrong `error_integral_reference` shape is reported in the first batch, before any subinterval is judged or a gradient is written, instead of before the first batch; and the warning for `trade_speed_for_memory=True` with an output that requires grad is logged at the end of the call (still only without a state), from whether the integral requires grad. For an integrand that draws from PyTorch's global random number generator (dropout, noise) the random starting mesh drawn after a given `torch.manual_seed` changes, since the one-point call no longer draws before it (and the test calls no longer draw before the first pass); results still repeat exactly for a given seed. A deterministic integrand gives the same results, bit for bit, unless `f` runs out of memory in its first call: the retries then start from the first pass instead of from a test call (with a limit of 60 points and the default gk21 mesh, 5 failed calls of 706 points (672 with `take_gradient=True`) instead of 2 of 175, the same batch size of 56 with `take_gradient=False`, and 42 instead of 56 with `take_gradient=True`, where every batch is whole subintervals of 21 points). The difference grows with the first pass when `f` cannot hold even 1,000 points: from a mesh of 500 subintervals (10,500 points) with the same limit, 18 failed calls of 39,773 points instead of 2 of 175, since each failed call shrinks by a quarter from 10,000 points (about 8 failed calls per factor of 10); for a limit of 1,000 points or more the failed calls are the same as before.
- **`integrate` no longer runs the memory benchmark.** Without `max_batch` or a state, its first call of `f` is its first pass, at most 10,000 points, and it lets the batch size grow by factors of 10 whenever more points are waiting, until `f` runs out of memory; the failed batch is retried at 0.75 times its size until it fits, and the batch size then stops growing. A given `max_batch` is used as it is. The benchmark's errors (memory growing faster than N², no reading above the noise floor, the 60 s limit) and its two warnings no longer come from `integrate`. Reaching the memory limit costs a few failed calls of `f` once per state (on an A100, for a network filling the GPU, 0.6 to 1.4 s more than a run with the right batch size); `total_mem_usage` now limits only the check before a backward pass.
- **With `take_gradient=True`, an out-of-memory error in `f` is retried with fewer subintervals** (it used to raise), and on a GPU a batch whose backward pass is predicted not to fit (its forward peak memory times the backward-to-forward ratio the previous batch measured, against the usable memory) is evaluated again, smaller, before any gradient is written.
- **A call needs a mesh or both bounds.** Without a mesh, `mesh_init` and `mesh_final` are required (`ValueError`); there are no default bounds. With a mesh, a missing bound is its end.
- **Bounds given with a mesh may differ from its ends.** A bound inside the mesh cuts it, and a bound outside it extends it (it becomes the new end point and the integration refines the new subinterval). Before, a bound passed with a mesh had to equal the mesh's end within the assertion tolerance (relative 1e-7 in float64, 1e-5 in float32) and was replaced by it; any other bound raised `AssertionError`. A bound within a few rounding steps of its mesh end (4 machine epsilons of the coarser of the bound's and the mesh's dtypes, relative to that end) replaces that end, without a near-zero-width subinterval.
- **Bounds must be tensors of shape `[T]` on every call**, with or without a mesh: a 0-d bound such as `torch.tensor(0.0)` raises `ValueError` (use `torch.tensor([0.0])`), and so does a Python number. 0-d bounds used to work.
- **A given mesh is validated:** shape `[M, T]` with at least two increasing points, else `ValueError` (it was a bare `AssertionError`). An integrand that does not return values of shape `[N, D]` also raises `ValueError` (it was an `assert`).
- **Integration bounds that are not increasing raise `ValueError`** instead of `AssertionError`. The check was an `assert`, which `python -O` removes; a reversed call then ran on, stored an out-of-order `mesh_optimal` with points outside the interval, and returned `converged=True`.
- **Every `integrate` argument after `mesh_final` is keyword-only**, so the removal of `same_f` cannot silently shift positional arguments.
- **The not-converged warning's remedies.** "Call again with the state it returned (state=state)", which works for a solver and for the one-shot `padaquad.integrate()`, is offered only when a finite error fails; when a NaN/Inf error ratio fails, the warning says to find where the integrand or the integral is NaN/Inf (`runtime_checks=True` raises at the first such value), since refining cannot remove it. With `take_gradient=True` it suggests `take_gradient=False` with `enforce_convergence` None or True.
- **`SolverBase._check_variables` fills in `f` and `y0` only** and returns `(f, y0)` (internal). The bounds are resolved once, in `_setup_integral_bounds`.

### Fixed

- **A subinterval too narrow to halve is accepted instead of split.** When the ends of a failing subinterval are neighboring floating-point numbers, its midpoint rounds onto one of them, and splitting it inserted a repeated mesh point: with `runtime_checks=True` the call raised an `AssertionError` with no message, and with `runtime_checks=False` it split the same subinterval again on every pass and never ended (for example `sign(t - 0.3)` on [0, 1] with `dopri5` and `atol=rtol=0`). Such a subinterval is now accepted, like one at `max_adaptive_splits`, in the loop, in the re-check of accepted subintervals and in the state's mesh, and the call ends with `converged=False`. This check runs on the device with no extra wait. Near a non-integrable singularity inside the interval, such as that of `1/(t - 0.5)**2` on [0, 1], the integrand's own rounding error (`t - 0.5` keeps few correct digits there) can fail the tolerance on every subinterval close to the singularity. With `take_gradient=True` (`gk21`, `atol=1e-6`, `rtol=0`, float64, `max_batch=100_000`) the call raised that `AssertionError` after 60 passes; it now refines for about 335 passes (723,684 mesh points, about 2 minutes and 1.3 GB on a CPU), until a pass reaches the subintervals at 0.5 and a node rounds onto 0.5, and then ends as with `take_gradient=False`, where this happens after 46 passes (`ValueError` naming t = 0.5, or an infinite integral with `runtime_checks=False`). With the default tolerances, whose `rtol` term grows with the integral, or a batch that holds every waiting subinterval, it ends after 46 passes. Pass `max_adaptive_splits` to stop it sooner.
- **An integrable singularity at a bound of 0 works with the Gauss-Kronrod methods.** `1/sqrt(t)` or `log(t)` on [0, 1] raised `ValueError` (`runtime_checks=True`) or returned NaN (`False`), because `f` was evaluated at the bound with weight zero; no other call of `f` is made at the bound (Changed: every point at which `integrate` calls `f` belongs to the integral). At a bound b other than 0 it works only while the subintervals next to b stay wider than about 230 times the spacing of the floating-point numbers at b (`gk21`): `1/sqrt(1 - t)` on [0, 1] still raises at the default tolerances in float32 and at `atol=1e-10` in float64, because a node rounds onto b (substitute `s = b - t`). The other methods evaluate the ends of every subinterval and still raise.
- **`integral_error` is exact after the re-check removes accepted subintervals.** The record stored absolute per-subinterval error estimates, so removing a subinterval subtracted |e| from the signed sum, off by up to 2|e| per removal; for `sin(2πt)` on [0, 1] (`bosh3`, `max_batch=16`, the former `conserve_memory=True`, `take_gradient=False`) it reported -1.2e-5 against a signed sum of -9.9e-8 over the returned subintervals. The record now keeps the signed estimates and subtracts them exactly; `loss_fxn`, the returned `mesh_quadrature_errors` and the optimal mesh still use absolute values, so meshes and integrals are unchanged.
- **A custom `loss_fxn` is exact after the re-check removes accepted subintervals.** Only the default loss was corrected on removal; a custom loss kept the removed subintervals' share and added their halves' (with `loss = 2 * integral` of an integral of 0.15: loss 0.51 and gradient 0.85 instead of 0.3 and 0.6). The loss of the removed subintervals, laid out as a per-batch result, is now subtracted, which is exact for any loss that is a sum over subintervals.
- **An integrand that returns another number of rows than points raises `ValueError` with `take_gradient=True` too.** Only `take_gradient=False` checked it; with `take_gradient=True` the values were reshaped into the subintervals without an error (an `f` returning two rows per point gave an integral with two components). Every call of `f` in the integration is now checked in one place, for both the shape [N, D] and one row per point, with one message.
- **With `take_gradient=True`, an integrand that holds one subinterval's points but not many more no longer raises `AssertionError`.** Without `max_batch` or a state, the test calls that ran out of memory shrank by a quarter until one ran, which could end below one subinterval (18 points for `gk21` when `f` holds 21 to 23; 56 for `cc65` when it holds 65 to 74), and the first batch, of no whole subinterval, raised `AssertionError` ("Not enough free memory to run 1 integration steps"). The test calls are gone: the first pass shrinks in whole subintervals, down to one.
- **`error_integral_reference` must have shape `[]`, `[1]` or `[D]`.** Another shape (for example two values for an integrand with one output) broadcast silently and changed the mesh; it now raises `ValueError` in the first batch, before any subinterval is judged or a gradient is written.
- **`conserve_memory=True` returned wrong integrals after an out-of-memory retry**, with `converged=True` (for example 0.38 for an integral of 0.54). The retry changed the batch size inside a pass, and nodes were paired with the integrand values of other nodes. No partly evaluated subinterval is carried between passes any more (every pass evaluates all waiting subintervals; see Changed), and the out-of-memory retry inside a pass, with calls that end inside a subinterval, is tested with and without `trade_speed_for_memory`.
- **A bound equal to the given mesh's end got no gradient.** With `mesh=result.mesh_optimal` and bounds equal to its ends (the reuse pattern), the bounds were replaced by the mesh's ends, which are detached from autograd, so `bound.grad` stayed `None` (and a bound within rounding of an end behaved the same). Every given bound is now an end point of the starting mesh, so it gets the gradient of any mesh end (d/db of the integral = f(b)).
- **A bound that requires grad raised "Trying to backward through the graph a second time" with `take_gradient=True`** once the integration took several batches, with or without a mesh: every batch's backward ran through the mesh's autograd graph, which the first one freed. Each batch is now evaluated on a detached copy of the mesh; the copies' gradients are summed on the mesh points and passed through the mesh's graph once, after the integration, so the time does not grow with the square of the number of batches.
- **`mesh_optimal` carried the autograd graph of a bound that requires grad.** A later call started from it then backpropagated into the earlier call's bound (its `.grad` changed although it was not passed), and after a `take_gradient=True` call it raised "Trying to backward through the graph a second time". `mesh_optimal` is now detached, so passing it as `mesh=` is safe; a bound's gradient within its own call is unchanged.
- **A cut could leave a subinterval one rounding step wide**, on which `interpolatory3_variable` returned NaN. Mesh points within the rounding tolerance of a bound are now dropped when the mesh is cut.

## [1.4.1] - 2026-11-15

### Changed

- **`mesh_optimal` merges neighbouring subintervals from a predicted merged error (new option `merge_rule`, default `"predicted"`).** 1.3.0 and 1.4.0 merged a pair only when its summed error ratio was below `remove_cut / 2**(error_exponent - 1)`, which assumes the error estimate grows `2**(k-1)`-fold when two subintervals merge. On wide subintervals it grows far less (about `2**8`–`2**9` where `2**20` was assumed for `gk21`, measured in a warm-started PINN training loop), so safe merges were refused and warm-started calls kept more subintervals than they needed: that training loop used 24–74 % more integrand evaluations under 1.3.0 than under 1.2.2. The integrals themselves were as accurate.
  - **How it works.** PadaQuad interpolates the integrand values already stored for the two neighbours onto the nodes the merged subinterval would have, and applies the method's weights. That gives the merged subinterval's integral and error estimate without evaluating the integrand. The pair merges when the larger of that error estimate and the difference from the sum of the two neighbours (the halves-versus-whole test of adaptive Simpson quadrature, Gander & Gautschi 2000), plus the neighbours' own errors, is below `remove_cut` times the tolerance. The difference term stops merges whose own error estimate would be blind, such as a kink that the merged nodes skip over. The prediction is linear in the stored values, so it uses weight vectors built once per ratio of neighbour widths and cached on the solver.
  - **Measured against 50-digit exact integrals** (14 methods, 17 integrands, 2.57 million pairs, tolerances down to the rounding level):
    - pairs whose merge can cost accuracy: 86, against 12,058 for the 1.3.0 merge rule and 23,215 for the 1.2.2 one;
    - none of the 86 are on a Gauss–Kronrod or Clenshaw–Curtis method;
    - worst: 4.35 times the tolerance (1.3.0: 66);
    - safe merges actually made on the high-order methods: 99 % (1.3.0: 50–74 %).
  - **Warm-start chains** (306 chains, 6 warm calls each): 13.7 % fewer integrand evaluations; no starting subinterval had to be split again (1.3.0: 5); none ended less accurate than its cold start (1.3.0: 2).
  - **Snapshots.** `n_optimal_mesh` changed in 90 of the 390 cases (86 smaller, 4 larger); `integral` and `integral_error` are unchanged in all of them.
  - **Cost.** The weight vectors are built once per distinct ratio of neighbouring widths, about 2 µs each for `gk21` and 20 µs for `cc65` on 8 CPU threads. Meshes grown from equal starting subintervals have few distinct ratios: 0.2–0.5 ms more per call on meshes of up to 64 subintervals, and on 10^6 equal subintervals building `mesh_optimal` takes 0.40 s against 0.30 s (gk21) and 0.77 s against 0.38 s (cc65). A starting mesh of many random subintervals has one ratio per pair, and its warm-started meshes keep them: with `N_init_steps=10**4` and a cheap integrand, a cold call took 93 ms against 24 ms (gk21) and 245 ms against 27 ms (cc65), and a warm call 11 ms against 4 ms and 31 ms against 7 ms. For an integrand that is expensive to evaluate the difference is small in relative terms. The prediction works in chunks of pairs, so its temporary memory does not grow with the mesh (at most about 0.25 GB for gk21 and 0.7 GB for cc65). Open question: `docs/issues/predicted-merge-cost.md`.
  - **The older merge rules stay available** as `merge_rule="power_law"` (1.3.0 and 1.4.0) and `merge_rule="sum"` (1.2.2). With a multi-coordinate integration variable (T > 1), `"predicted"` falls back to `"power_law"` with a warning.
  - **Limit, shared by every merge rule:** a feature of the integrand that lies between the stored nodes cannot be seen.

  Plan, evidence and its adversarial reviews: the commits of PR #69.

### Fixed

- **A node no longer lies past the end of its subinterval.** Node i of a subinterval was placed at `left + c_i * (right - left)`; when `right - left` rounds (float32, wide subintervals) the last node came out one rounding step past `right`, so it lay past the next subinterval's first node and, on the last subinterval, outside the integration interval. Nodes are now placed with `torch.lerp`, whose nodes at c = 0 and c = 1 are the mesh points bit for bit. The visible failure was an `AssertionError` in `_merge_excess_nodes` (node order after merging): the README's gradient example, which runs in float32, failed for 37 of 2,000 random starting meshes with `merge_rule="predicted"` and 1 of 1,000 on 1.4.0. Nodes with c ≥ 0.5 can move by a rounding step, so results can change at the rounding level.
- **Building `mesh_optimal` no longer takes time quadratic in the number of subintervals.** `_rec_remove`, which picks which of the flagged neighbouring pairs are merged, un-flagged about two entries per pass over the whole mask, so a call in which most pairs qualified for merging spent almost all its time there: 9.1 s of a 9.5 s call with 10^5 subintervals, for gk21, cc65 and dopri5 alike (about 15 minutes expected at 10^6). It now computes the same result in one pass (within each run of flagged pairs, keep every other one starting from the first): 0.07–0.10 s for the same calls. The output is unchanged, checked against the old loop on 2,580 random masks in the test suite, and the mask passed in is no longer modified. Details: PR #69.

## [1.4.0] - 2026-11-15

### Removed

- **The submodule `padaquad.integrate`.** It had the same name as the function it defined, so `padaquad.integrate` meant the module or the function depending on how it was imported. Its code is now the private module `padaquad._frontend`. `from padaquad import integrate, adaptive_quadrature` is unchanged; `from padaquad.integrate import integrate` now raises `ModuleNotFoundError`; use `from padaquad import integrate`.
- **`max_path_change`.** The constructor argument and the early exit it controlled are gone; `max_adaptive_splits` bounds refinement instead. Passing `max_path_change=` now raises `TypeError`. To migrate:
  - To limit how much a call refines, set `max_adaptive_splits`. The call returns `converged=False` when it stopped short of the tolerance, and repeated `same_f=True` calls refine further from `mesh_optimal`, which splits the failing steps (as the early exit's stored mesh did; in cumulative mode a failing step can instead be merged with a right neighbour whose running integral, and so tolerance, is much larger).
  - To see how much of the starting mesh failed, read `n_start_steps_split` / `percent_start_steps_split` (below). With `max_adaptive_splits=0` nothing is split, so read `converged`, or `(result.error_ratios >= 1).float().mean()`, the fraction of steps that failed when accepted (with `error_norm="failure_fraction"`, `error_ratios` holds failure fractions, so compare with `> mesh_failure_tolerance` instead).
  - What is lost is the conditional behaviour "refine fully only when few starting steps fail".
- **No positional constructor arguments.** `max_path_change` was the 4th positional constructor argument. Every constructor option is now keyword-only (see Changed), so passing any of them by position raises `TypeError`. A `max_adaptive_splits` that is not an integer (`int` or numpy integer) raises `TypeError` (a negative one `ValueError`), so a float meant for `max_path_change` cannot act as a cap.

- **Support for Python 3.10.** PadaQuad now requires Python 3.11 or newer (`requires-python = ">=3.11"`), and CI tests Python 3.11 and 3.12. numpy 2.2.6 is the last numpy release that installs on Python 3.10, and its type stubs give `np.ndarray` no default type arguments, so the CI type check (`disallow_any_generics`) failed on it. The numpy used in CI (`tests/requirements.txt`) moves from 2.2.6 to 2.4.6, the newest release that supports Python 3.11.
- **`_get_num_tableau_c()`** on both solvers. It recomputed `solver.C`; use `solver.C`.
- **`padaquad.runge_kutta`** (its contents moved as described under Changed), **`_VariableSubclass`**, **`_VARIABLE_SECOND_ORDER`**, **`_Interpolatory3Variable`** (use `VARIABLE_METHODS["interpolatory3_variable"]`) with its `b_delta`, `_b0`, `_ba`, `_b1` and `tableau_b` (now the instance's `weight_function`), **`n_tableau_c`** (use `method.n_nodes`), **`_get_tableau_b`** (use `solver.method.weights(nodes)`), **`_Tableau.clone`** (use `MethodClass.clone`), and the solver attributes **`order`** (never read; use `solver.method.order`) and **`Cm1`** (use `solver.C - 1`).
- **`_sort_evals_into_mesh` and `_sort_evals_into_mesh_full_nodes`**, which nothing called.

### Added

- **`limit_benchmark_time` (solver option, default True).** The memory benchmark raises an error when it cannot measure the memory of `f` within 60 s; `limit_benchmark_time=False` removes that limit, for an integrand so slow that the measurement needs longer (for example a model of 5 s per call using 1 KiB per point, whose readings reach the 4 MiB noise floor only after 12 doublings of N, at N = 4096, and allow a fit two doublings later: 15 calls, 75 s). The time-limit errors name the option. `padaquad.integrate` accepts it too.

- **Split statistics on `IntegrationResult`.** `n_start_steps` (steps in the starting mesh: the caller's `mesh`, the mesh stored by `same_f=True`, or a fresh one), `n_start_steps_split` (starting steps split at least once, including splits by the re-check of accepted steps), the property `percent_start_steps_split` (`100 * n_start_steps_split / n_start_steps`), and `max_split_depth` (the largest number of times any one step was halved). They are read off the per-step split counter, which is now always kept (it was kept only when a cap was set); results are unchanged. Splits made afterwards to build `mesh_optimal` are not counted. All three are `None` in the per-batch result passed to `loss_fxn`.

- **Type checking is enforced in CI, and PadaQuad ships its types.** `mypy padaquad/` runs in the `tests` workflow (both Python versions) with every function annotated and every function body checked (`disallow_untyped_defs`, `check_untyped_defs`, `disallow_any_generics`, `no_implicit_optional`; see `[tool.mypy]` in `pyproject.toml`). Before, about 37 functions had no annotations, so mypy skipped their bodies. The package now contains the `py.typed` marker (PEP 561) that `pyproject.toml` already listed but that did not exist, so type checkers in projects that use PadaQuad see its annotations, and `padaquad/__init__.py` defines `__all__`. `mypy` is pinned to `~=2.1.0` in the `dev` extras so a new mypy release cannot fail CI on its own.

- **`MethodClass.measure_degree()` measures a method's polynomial degree from its tables.** It integrates the Legendre polynomials P_k(2t - 1), k = 0 … 2C, over one subinterval with the method's weights and with the lower-degree weights of its error estimate, and returns both measured degrees and the errors (`DegreeMeasurement`). `UNIFORM_METHODS["gk21"].measure_degree()` gives degree 31 and error-estimate degree 19. Legendre polynomials replace the powers t^k of the old exactness test: a method's error on (2t − 1)^(d+1) is its Legendre error times (k!)² 2^k / (2k)!, which is 2.6e-17 for gk31 and below float64 rounding (for powers of t itself the factor is (k!)² / (2k)!, smaller still), so the power test reported degree 63 for gk31, 37 for cc33 and at least 130 for cc65. `tests/test_exactness.py` now checks every method in both directions (exact through its degree, error at least 1e-8 one degree further; the smallest such error is 4.2e-6, for cc65), checks every `error_exponent`, and checks the stored tables in 60-digit arithmetic (mpmath, installed with torch through sympy).

Both exit with status 1 when a check fails, and the test suite runs them.

It now compares torchdiffeq `dopri5`, PadaQuad `dopri5` and PadaQuad `gk21` on six integrands with known integrals at two tolerances, recording median time over repeated runs, integrand evaluations, absolute error, hardware, versions and git commit, in `docs/performance/results_<device>.json`. ### Changed

- **`f_unit_mem_size` is replaced by `f_mem_coeffs`.** The solver attribute set by the memory benchmark is now the fit (a, b, d), in GB, of the memory of one call on B points, a + b·B + d·B² (including the gradient factor and the reading's error), instead of one cost per evaluation. Automatically chosen batches use 75 % of the usable memory (`_MEMORY_BUDGET`), so they are 25 % smaller than before for an integrand whose memory grows linearly. A memory benchmark that cannot measure the memory of `f` (no reading reaches the noise floor, or the readings do not allow a fit within 60 s) now raises an error asking for `max_batch` instead of choosing a batch of up to 1e9 points. `scipy` is imported only when the benchmark runs; the import adds about 0.3 s to the first benchmark in a process (measured on an Apple-silicon Mac, where the whole benchmark for `torch.sin` took about 0.05 s before).
- **`converged` reports whether the returned integral meets the tolerance.** It was `True` on every call except a `max_path_change` early exit, including calls where `max_adaptive_splits` left steps failing. Every accepted step is now judged against the final integral (in cumulative mode, the final running integral through the step), the reference `mesh_optimal` is built with (also when `error_integral_reference` is given), and `converged` is `False` if any fails or has a NaN/Inf error ratio. A step accepted at the `max_adaptive_splits` cap usually fails this check, but can pass it. A warning then reports the number and percentage of failing steps, the largest error ratio, and the failing steps' summed error estimate next to the total over all finite steps and `|integral|` (for D > 1, all three for the output component with the largest relative failing error), followed by the remedies that apply to the call's settings. Steps are accepted against the running integral, and with `take_gradient=True` (the default) accepted steps are never re-checked, so `converged=False` also appears without a cap. Over 576 uncapped `take_gradient=True` runs (bosh3, dopri5, gk7, gk21, cc9, cc17; six integrands on [0, 1], three of them cancelling; an rtol-dominated and an atol-dominated tolerance; two seeds; absolute and cumulative mode; the `"2"` and `"failure_fraction"` norms; eight steps per batch), 47 (8.2 %) returned `converged=False`, all in absolute mode, where the tolerance follows the running total; the median worst ratio of the `"2"`-norm failures was about 1e4, from cancelling integrands whose total is near 0. The same 576 runs with `take_gradient=False` all converged. Integrals are unchanged; the result only reports what it did not report before. `error_ratios` still holds each step's ratio at acceptance, so it can show every step passing while `converged` is `False`. `converged` is `None` in the per-batch result.

- **`IntegrationResult` is keyword-only and its fields are required.** Fields typed `torch.Tensor` used to default to `None`. They are now required, and the dataclass accepts keyword arguments only, so a result built without one of them raises `TypeError` instead of carrying a `None` that fails later. Three fields can still be `None`: `mesh_optimal` (in the per-batch result passed to `loss_fxn`, where no optimal mesh exists yet; always a tensor on a returned result), `tracked_variables` (when the integrand returns none), and `loss` (in the per-batch result before `loss_fxn` runs). The per-batch result now carries `y0` as a zero tensor instead of the integer `0`. Code that builds an `IntegrationResult` itself must pass every required field by keyword.
- **A missing integrand raises `ValueError`.** `integrate()` with no `f`, here or at construction, now raises `ValueError` from `_check_variables`; it was an `AssertionError`.
- **`max_batch` is always a Python `int` inside the integration loop.** When the memory budget exceeded the remaining work, `max_batch` became a 0-d tensor holding that count; it is now `min(max_batch, int(remaining))`, the same value. No change in results.
- **One abstract `MethodClass` for every quadrature rule.** The uniform rules (`MethodClass` with a `_Tableau`) and the variable rules (`_VariableSubclass` with `tableau_b(c)`) were two unrelated class families, and each solver carried its own copy of node placement, method setup, the integral computation and the weight lookup. `MethodClass` is now an abstract base declaring `node_fractions()`, `weights(nodes)`, `to_dtype`, `to_device`, `n_nodes` and `clone()`; Two generic classes implement it from data, and every registered rule is an instance of one of them: `UniformMethodClass` from a fixed `_Tableau`, and `VariableMethodClass` from node fractions and a module-level `weight_function` of the normalized node positions (`interpolatory3_variable` is `VariableMethodClass` with `_interpolatory3_weights`). Both reject malformed node fractions (not 1-D, not from 0 to 1, or decreasing) with `ValueError`, and `VariableMethodClass.weights` rejects a weight function that does not return `[N, C]`. Node placement, `_set_solver_dtype` and `_calculate_integral` now exist once, in `AdaptiveQuadrature`. Consequences for code that uses these internals:
  - `MethodClass(order, error_exponent, tableau)` can no longer be constructed; use `UniformMethodClass`.
  - Both registries hold instances that `_get_method` clones per solver, so `VARIABLE_METHODS[name]()` no longer works; `VARIABLE_METHODS["adaptive_heun"]` is the same object as `UNIFORM_METHODS["adaptive_heun"]` (its two nodes are the panel ends, so its weights cannot depend on positions).
  - `method.weights(nodes)` returns `b` and `b_error` shaped `[N, C, 1]` for every rule (the uniform weights were `[C, 1]`, adaptive heun's `[1, C, 1]`); stored tables are `[C]`, including adaptive heun's, which was `[1, 2]`.
  - An unknown method name raises `ValueError` listing the valid names, from `_get_method`; it was an `AssertionError` in the solver or a `KeyError` in `_get_method`.
  - `UniformAdaptiveQuadrature` and `VariableAdaptiveQuadrature` are defined in `padaquad.quadrature`, and `adaptive_quadrature` in the private module `padaquad._frontend` (see Removed); `from padaquad import ...` is unchanged.

  No numerical result changes: 1,280 integrations (both sampling modes, float32 and float64, gradients, D = 3, several batches, `conserve_memory`, warm starts) give bit-identical tensors.
- **The variable solver detaches its error estimates,** as the uniform solver already did (they only drive accept/split decisions). With `take_gradient=False` and a learnable integrand, its `integral_error` and `mesh_quadrature_errors` no longer require grad; the values are unchanged.
- **The quadrature tables are built without numpy.** Gauss-Kronrod tables are built with torch and Clenshaw-Curtis tables with Python floats and `math.cos` (same summation order), so PadaQuad no longer imports numpy and every table is bit-identical to before.
- **Both solver types build their method in one place.** The variable solver built its method in `__init__` with its own copy of `_get_method`'s steps; both solvers now build it in `_set_solver_dtype`, which `SolverBase.__init__` calls when it sets the dtype (the uniform solver's `_setup_method`, which only `_set_solver_dtype` and `__init__` called, is merged into it). `AdaptiveQuadrature.__init__` no longer resets `method`, `order`, `C` and `Cm1` to `None` after they were built, and the uniform solver no longer builds its method twice. A dtype change now rebuilds the variable method from its float64 definition rather than converting the existing one. No change in results: the variable methods' coefficients (0, ±1/2, 1) are exact in float32 and float64.
- **Tracked variables are stored as one record entry each** (`tracked_variables_0`, `tracked_variables_1`, …) instead of a list under one key, so every record value is a tensor and the record code has no special case for them. When the set of tracked variables differs between two recorded batches, `_record_results` now raises `ValueError` naming both sets of record keys; before, tracked variables that first appeared in a later batch were dropped without a message, and tracked variables that disappeared raised `TypeError`. An integrand that returns an empty tuple of tracked variables now gets `tracked_variables=None`, the same as an integrand that returns none, in both the per-batch and the returned result; before, the returned result held `()`. No other change in results.
- **`SolverBase.integrate` declares the arguments every solver accepts,** in `AdaptiveQuadrature.integrate`'s order (`f, y0, mesh, mesh_init, mesh_final`, then keyword-only `f_args`). It listed `mesh_init` and `mesh_final` before `mesh`, the opposite of the only implementation. `_merge_excess_nodes` is declared as an abstract method of `AdaptiveQuadrature` with its real signature (`_compute_nodes` is now one shared method; see the `MethodClass` entry above).

- **Methods store their polynomial degree; `order` is `degree + 1`.** `UniformMethodClass(degree, error_exponent, tableau)` and `VariableMethodClass(degree, error_exponent, c, weight_function)` take `degree`, the highest polynomial degree the method integrates exactly, in place of `order`, which is now a read-only property returning `degree + 1` (Gonnet 2012, ACM Comput. Surv. 44(4), Sec. 1 (arXiv:1003.4629v2, p. 3)). Both reject a `degree` that is not an int ≥ 0 and an `error_exponent` that is not an int ≥ 2 with `ValueError`. The degrees: adaptive_heun 1, fehlberg2 1, bosh3 2, dopri5 4; gk7 11, gk15 23, gk21 31, gk31 47; cc5 5, cc9 9, cc17 17, cc33 33, cc65 65; interpolatory3_variable 2 (3 with its middle node at the center). `order` therefore changes from 11/23/47 to 12/24/48 for gk7/gk15/gk31 and from 5…65 to 6…66 for cc5…cc65; the README and code comments that gave those methods a degree one too low are corrected. No algorithm reads `order`; integrals are unchanged.

- **The solver constructor is keyword-only and names every option.** `AdaptiveQuadrature.__init__` (inherited by `UniformAdaptiveQuadrature` and `VariableAdaptiveQuadrature`) now lists every option: `f`, `method`, `atol`, `rtol`, `mesh_init`, `mesh_final`, `y0`, `remove_cut`, `max_batch`, `total_mem_usage`, `max_adaptive_splits`, `use_absolute_error_ratio`, `error_norm`, `mesh_failure_tolerance`, `runtime_checks`, `dtype`, `device`, `output_speed_info`, plus the multi-GPU options of `DistributedEnvironment`. Before, the options were spread over three constructors joined by `*args`/`**kwargs`, and positional arguments filled `remove_cut`, `max_batch`, … in order. Passing any option by position now raises `TypeError`; an unknown keyword raises `TypeError` naming the solver class (it named `DistributedEnvironment.__init__`). `SolverBase.__init__` takes its options as required keywords, so each default is defined once. `remove_cut >= 1` raises `ValueError` (it was an `assert`).
- **`adaptive_quadrature(sampling_type, method, **options)`.** `method` is now the second positional argument, as in `integrate(f, method, ...)`. Before, `adaptive_quadrature("uniform", "dopri5")` put `"dopri5"` into `remove_cut` and failed with `TypeError: '<' not supported between instances of 'str' and 'float'`.
- **`padaquad.integrate(f, method, sampling, **options)` accepts every solver option.** Each keyword goes to the solver's `integrate` call if it is one of that call's arguments, and to the constructor otherwise; the defaults are the solver's (one source). `f_args`, `same_f`, `N_init_steps`, `random_initial_mesh`, `loss_fxn`, `error_integral_reference` and `conserve_memory` used to raise `TypeError` because they were sent to the constructor. All options after `sampling` are keyword-only. `sampling` accepts every name `adaptive_quadrature` accepts. `method=None` (the default of the constructor, the factory and `integrate()`) means the sampling type's default method, from `DEFAULT_METHODS` in `padaquad/base.py`: `"gk21"` for uniform sampling and `"interpolatory3_variable"` for variable sampling. Before, the one default `"gk21"` made `adaptive_quadrature("variable")`, `VariableAdaptiveQuadrature()` and `integrate(f, sampling="variable")` raise `ValueError: Unknown method 'gk21'`.
- **Sampling-type names are case-insensitive** in `get_sampling_type` (and so in `adaptive_quadrature`), as `integrate(sampling=...)` already was.

### Fixed

- **The memory benchmark no longer assumes memory grows linearly with the number of points.** It called `f` on N = 1, 10, 100, … points and made the next call whenever 10·M fit in usable memory (M the memory of the last call), then sized batches as usable memory ÷ (memory per point). For an integrand whose memory grows like N² (for example, per-point gradients with `torch.autograd.grad(..., is_grads_batched=True)`), the next call needs about 100·M. popcornn reported that on its 16 GB CI runners the benchmark called N = 10,000 points (about 51 GiB) and Linux killed the process, which raises no catchable error; when the benchmark survived (only the 1 s limit stopped it), the batch, about 11,500 points, would have needed about 68 GiB (extrapolated from its readings). Now:
  - **Readings.** A reading is never below the bytes of the call's input and output tensors (alive when it is taken), so it is never 0. A reading counts as reliable when it reaches the reader's noise floor: 10 KB on a GPU (whose counter is exact), 4 MiB on a CPU (smaller resident-memory readings are mostly noise: 0, or steps of 2 MiB). On Linux, glibc's `malloc_trim(0)` runs before each reading, so memory `f` takes from memory the process freed earlier is counted (popcornn's readings on Linux came out as low as 0 MiB where about 25 MiB was true; the trim recovered them). On macOS and Windows no such call exists (macOS's `malloc_zone_pressure_relief` released nothing in a test): there, in a process that has already evaluated `f`, readings can be far too low, and the start warning says so and recommends `max_batch`. In 14 `integrate()` calls in one process on an Apple-silicon Mac (a popcornn-like integrand using 266 bytes·N², 4 GB usable), 3 batches needed 0.65–0.97 times the usable memory, 6 needed 1.2–35 times it, and 5 calls raised; the benchmark's own test calls needed more than the usable memory in 7 of the 14 (up to 6.9 times it). In an earlier run of the same kind, one batch was 1e9 points (three reliable readings that did not grow, so the fit was flat). Only the first call in the process gave a batch below the usable memory every time (0.76–0.86 times it, in three runs). On these readers the batch is now also capped at the largest test call, which ran (at least one subinterval's nodes, the smallest batch `take_gradient=True` can evaluate); for an integrand whose cost per point stops changing early this cap can be well below what fits (for 1 MiB + 1 KiB per point with 100 GB usable, 1e7 points where the fit allows 7.9e7). The benchmark's own test calls are not bounded this way. The Linux error allowance E counts only the CPUs the process may run on (`os.sched_getaffinity`), twice, because a reading is the difference of two counts: 1 MiB on a 4-CPU machine, and 16 MiB instead of 512 MiB on a 256-CPU node pinned to 4 CPUs (1 GiB when the process may use all 256).
  - **The fit.** Only reliable readings are fitted, as a + b·N + d·N² with a, b, d ≥ 0 (`scipy.optimize.nnls`). The fit is *ready* when it uses three reliable readings and its memory grows by at least the noise floor from the first of them to the last; the search goes on until it is. Readings that grow less are within the noise, and readings that do not grow at all (a slow integrand with a fixed workspace, read in whole pages) gave a flat fit allowing 1e9 points. Before the fit is ready, each next call is sized by the worst case such a fit allows through the reliable reading with the largest N (or the latest reading, if none is reliable): y(k·N) ≤ k²·y(N).
  - **The next call** is not 10·N but min(step·N, the largest N whose predicted memory fits in 75 % of the usable memory, the largest N predicted to take at most 1 s), with step 2 after a call that took more than 0.1 s on a reader that counts reused memory (a GPU, or Linux with `malloc_trim`) and 10 otherwise. The time bound allows doubling N for the first two calls and while the fit is not ready (the 1 s limit is extended one doubling at a time). No call is started that is predicted to end past a total of 60 s for the whole measurement, the first two included (the time of the next call is predicted from a fit of the times, or as growing like N² before three calls; a call that takes longer than predicted cannot be interrupted, so the 60 s are checked again after it).
  - **Stops.** The search stops, keeping the fit, when the cost per point changes by less than 1 % over each of the last two calls with the last three readings reliable and the fit ready (a reliable reading larger than these three, from memory `f` allocated in that call only, can keep the fit from growing by the floor), when a call takes longer than 1 s (with the fit ready), at N = 1e9, when the next call would be less than 2·N, or when the measurement passes 60 s with the fit ready. It raises a `RuntimeError` that explains what happened, lists every reading (N, MiB, seconds, and which were below the noise floor) and asks for `max_batch` when: a call uses more than 3 times the memory that growth like N² allows from an earlier reliable reading, M > 3·(N/N_i)²·(M_i + E), tested against the earlier reliable reading with the smallest bound (either the memory grows faster than N², which the fit cannot follow, or, on a CPU, the earlier reading missed reused memory: an integrand whose memory grows exactly like N² can then occasionally raise on macOS); the fit is not ready when the 60 s run out, or when the next call needed for it would fit in memory but is predicted not to finish in time (when it would not fit either, the memory budget ends the search; these errors name `limit_benchmark_time`); or no reading is reliable when the search ends otherwise. When the memory budget (or an out-of-memory error, or N = 1e9) ends the search before the fit is ready, the batch uses the worst case N² through the reliable reading with the largest N, and the end message says so. In simulations of integrands growing like N or N² (16 B·N, 1 MiB + 1 KiB·N, 8 MiB + 64 B·N, 8 B·N², 0.25 MiB + 8 B·N²; 150 runs each, with 10× and with 2× steps), readings off by 0.5–1.5 times gave no false faster-than-N² error. Readings of 0 in 30 % of the calls (memory hidden from the reader, as on macOS in a process that has evaluated `f`) gave false errors for 1 MiB + 1 KiB·N in 85 of 150 runs with 10× steps (125 with 2× steps, which only readers that see reused memory take) and for 8 MiB + 64 B·N in 19 of 150 with 2× steps, the same counts as before the comparison with every earlier reading: a reading of 0 is raised to the bytes of the input and output, which at a million points reaches the noise floor while being far below the true memory.
  - **The batch** is the largest B whose fitted memory s·((a + E) + b·B + d·B²) fits in 75 % of the usable memory (s = 2.1 with `take_gradient=True`, else 1). Run on the readings popcornn reported (memory 0.508 GiB and time 1.23 s at N = 1000, about 12.3 GiB usable, `take_gradient=True`) with fake memory and time, the benchmark of the first version of this change gave about 2,960 points (about 4.4 GiB forward, 9.3 GiB with the factor 2.1) instead of 11,500; popcornn itself was not rerun with this version.
  - An out-of-memory error during the benchmark at N > 1 caps the batch at 0.75·N for the rest of the `integrate` call (the cap the batch loop already uses after such an error) instead of estimating a cost from the free memory.
  - After an out-of-memory error, the batch loop retries with 0.75 times the batch that failed. It took 0.75 times the cap `_oom_max_batch` whenever one was set, and the benchmark's caps (above, and on macOS and Windows on every call) can be far above the batch: in a test with a cap of 1000 points, a 44-point batch that ran out of memory above 29 points was retried 11 times at 44 points before shrinking.
  - The user guide lists the benchmark's known limitations ("Limitations of the memory benchmark", in Devices and memory), and the benchmark's start warning links to that list, says the benchmark may underuse the hardware, and says that passing your own `max_batch` avoids all of it, while reusing the benchmark's result (`solver.get_max_batch()`, `same_f=True`) only saves its time.
  - Limits: growth faster than N² that is not caught is underestimated: memory growing like N^p shows it only across a range of N over which (N/N_i)^(p−2) exceeds 3, so N³ is caught once two reliable readings are more than 3 times apart in N, and N^2.2 not before 243 times apart (comparing only with the previous reading, as before this change, let N³ pass after every 2× step); a large fixed cost delays this, because every bound includes it (in a simulation with 2× steps and 100 GB usable, 512 MiB + 10,000 bytes·N³ was not caught up to N = 128 and gave a batch needing 1.48 times the usable memory); an N² term too small to show in the reliable readings, or hidden by their noise, is missed when the cost per point looks constant; the before/after reader on macOS and Windows misses memory `f` frees before returning, and the CPU readers without `malloc_trim` (macOS, Windows, musl, or a preloaded allocator such as jemalloc) miss memory `f` reuses.
- **Test coverage reaches Codecov, measured on the installed package.** Codecov showed 0% for two reasons:
  - **Nothing was measured.** CI installs PadaQuad non-editable, as users do, so the tests import the copy in `site-packages`, while `source = ["padaquad"]` made coverage watch the `./padaquad` checkout, which never ran ("No data was collected"). `[tool.coverage.run]` now measures the imported package (`source_pkgs`) and `[tool.coverage.paths]` reports it under `padaquad/`. Run `pytest --cov`: `--cov=padaquad` restores the old setting. The full suite measures 94%; `fail_under = 90` (`[tool.coverage.report]`) fails a `--cov` run below that, so a run that measures nothing can no longer pass.
  - **Uploads went to the old repository name.** Since the rename from `torchpathdiffeq` (2026-05-30) the uploader sent reports to `khegazy/torchpathdiffeq`, where they were discarded, and the step still passed. The upload (now `codecov/codecov-action@v7`) authenticates with GitHub's OIDC identity of this repository, so no Codecov token is stored; a PR from a fork, which cannot get that identity, uploads without a token and does not fail its CI on a rejected upload.
- **The PyPI upload runs when a release is published.** `.github/workflows/release.yaml` ran on the `created` activity, which GitHub does not send for a draft release (GitHub Docs, "Events that trigger workflows", `release`), so a release saved as a draft and published later was never uploaded (the web interface may save a new release as a draft). It now runs on `published`, the activity the documentation workflow uses too.
- **The re-check of accepted steps used the wrong running integral in cumulative mode.** With `use_absolute_error_ratio=False` and `take_gradient=False`, each recorded step is re-judged against `|running integral through it|`; that sum was taken over the recorded steps only, leaving out the batch just evaluated, so steps to the right of a batch step were judged against the wrong value and could be left failing. It now uses the running integral of the record and the batch together. Cumulative-mode results can change; absolute-mode results do not.

- **Known limitation documented: `fehlberg2`'s error estimate ignores curvature.** Its weights [1/512, 255/256, 1/512] and the lower-degree weights [1/256, 255/256, 0] make nearly the same error on a curved integrand (0.25098 and 0.24902 for t² on [0, 1], exact 1/3), so their difference, the error estimate, keeps only (f(end) − f(start)) / 512 times the width. On `damped_sine` at tolerance 1e-6, subintervals with estimates near 1e-7 have true errors near 1e-4, and the total error (1.0e-4) is larger than 84 subintervals × 1e-6. The behaviour is unchanged; `examples/verification/integral_accuracy.py` reports it as `[KNOWN]` and the README warns about it.

- **A failed constructor no longer prints a second error.** `SolverBase.__del__` called `end_process` on a half-built object, so a constructor error was followed by an ignored `AttributeError: ... has no attribute 'is_distributed'`.

- **Two Gauss-Kronrod digits beyond float64 precision.** gk21 `wgk(3)` differed from Netlib QUADPACK in its 33rd digit and the gk7 node 0.4342437… from its 28th significant digit; both now match an 80-digit computation. The float64 tables are unchanged.
- **Descriptions corrected to match the code.** The variable-sampling solver does not reuse integrand values when it splits a subinterval (`_evaluate_adaptive_nodes` is not called by `integrate()`), so `interpolatory3_variable` always has its middle node at the center, where it is Simpson's rule; the README, docstrings and glossary said otherwise. `adaptive_heun`'s error weights subtract the right-endpoint rectangle rule, not Euler's method (same size, opposite sign). `integral_error` is approximate with `take_gradient=False` when the re-check removes a subinterval (the absolute value of its estimate is subtracted from a signed sum). No behavior changed.

## [1.3.0] - 2026-11-10

### Added

- **`adaptive_quadrature` defaults to uniform sampling.** `sampling_type` was a required argument, so `adaptive_quadrature(method="gk21", ...)`, as written in the README's warm-start example, raised `TypeError: missing 1 required positional argument: 'sampling_type'`. It now defaults to `DEFAULT_SAMPLING_TYPE` (`"uniform"`, defined in `padaquad/base.py`), the same constant that now sets the default of the `padaquad.integrate()` wrapper's `sampling` argument, so both defaults change together.

### Changed

- **The memory benchmark now measures the memory cost of one integrand evaluation.** `_setup_memory_checks` measures one number, c (`f_unit_mem_size`), the memory one evaluation of `f` uses; the batch size is still computed at every evaluation from live free memory (usable memory ÷ c). Before, nothing was measured: when a test call took longer than 0.1 s the code assumed 100·N points would fill memory, so c was about 100 times too small and batches about 100 times too large. The 1.2.2 entry below claimed the result "never extrapolates past the largest tile actually validated"; that was wrong. Now, for N = 1, 10, 100, … points, M (the memory one call used) is measured and c = s·(M + E)/N, with s = 2.1 for `take_gradient=True` (a heuristic for backpropagation) and 1 otherwise:
  - **CUDA:** peak allocated memory during the call minus allocated memory before it (`torch.cuda.reset_peak_memory_stats` / `max_memory_allocated` on the solver's device). This counts memory `f` frees before returning, such as the intermediates of a Jacobian computed inside `f`. It resets the device's peak counters, including `max_memory_reserved`.
  - **CPU on Linux:** the process's peak resident memory (`VmHWM` in `/proc/self/status`), reset before each call by writing `5` to `/proc/self/clear_refs`, which also resets the peak your own `getrusage` or `/usr/bin/time` report. `ru_maxrss` is not used because it also includes the peak of the process this one was started from, so in a worker started by a larger process (`subprocess`, multiprocessing `spawn`, a Jupyter kernel) it would read no memory use. The kernel's per-CPU counters can read low by up to E = cores·max(32, 2·cores) pages (`lib/percpu_counter.c`), so E is added (1.5 MiB on 12 cores, 512 MiB on 256 cores).
  - **Other CPUs (macOS, Windows):** resident memory after the call minus before. Memory `f` frees before returning is missed there.

  The search stops when c changes by less than 1 % from N/10 to N, a call takes longer than 1 s, N reaches 1e9, or the next call is predicted not to fit (10·M > usable memory). After an out-of-memory error at N, the c measured at the previous N is kept if that N was at least 100; otherwise c = max(previous c, s·F/(0.75·N)), F the free memory before the call. The one-point check of `f` in `integrate()` now runs before the benchmark, so one-time costs (CUDA start-up, lazy model loading) stay out of it. A single evaluation that does not fit raises a clear `torch.OutOfMemoryError` instead of tripping an internal `assert`; any other failure of the measurement stops the run with a `RuntimeError` saying the memory could not be measured and that `max_batch` must be passed, with the original error attached.
- **`integrate()` now takes its dtype from `mesh_final` when that is the only bound given.** `integrate()` passed `mesh_final=mesh_init` to `set_dtype_by_input`, so when `mesh` and `mesh_init` were both `None` the dtype of `mesh_final` was ignored and the integral ran in the solver's construction dtype. A call that passes only `mesh_final` (including through the `padaquad.integrate()` wrapper) now follows the rule that already applied to `mesh` and `mesh_init`: the solver switches to `mesh_final`'s dtype. This can lower precision: `mesh_final=torch.tensor([2.0])` (float32 by default) on a float64 solver now integrates in float32. An integer `mesh_final` passed on its own now raises `ValueError: Given dtype must be torch.float64 or torch.float32; got torch.int64`, as an integer `mesh_init` already did; pass a floating-point tensor.
- **An unknown `sampling_type` now raises `ValueError` with a message, instead of a bare `KeyError`.** `adaptive_quadrature('bogus')` (and `get_sampling_type('bogus')`) raised a bare `KeyError: 'bogus'`; they now raise `ValueError` naming the bad value and listing the valid names. A sampling type that exists but is not adaptive (`steps.FIXED`, `'fixed'`) or a value of the wrong type also raises `ValueError` naming it and the two supported types; previously that was a `ValueError` with no message. Code that caught `KeyError` here must catch `ValueError`.
- **PadaQuad now requires `torch>=2.4`.** The out-of-memory handling (`_is_out_of_memory` and the batch-reduction re-raise) uses the top-level `torch.OutOfMemoryError`, which first exists in PyTorch 2.4.0 ([release notes](https://github.com/pytorch/pytorch/releases/tag/v2.4.0), [#121702](https://github.com/pytorch/pytorch/pull/121702)). `pyproject.toml` listed `torch` with no lower bound, so on an older torch the first out-of-memory error would have become an `AttributeError`. 2.4 is the first version where that name exists, not a tested minimum: the code has been run on torch 2.8, and CI installs the latest release.
- **The solver no longer changes process-wide PyTorch state.** It used to call `torch.cuda.set_device` for CUDA and `torch.set_default_device` for CPU (and `torch.cuda.init`), which affected all other code in the process. Only distributed runs still call `torch.cuda.set_device`, which NCCL needs. `solver.device` is now always one `torch.device`; a CUDA device always carries an explicit index.
- **The memory benchmark's messages.** When it starts, a warning explains that `max_batch` is being measured because adaptive refinement changes the evaluation batch at each step, that the measurement is slow and runs on every `integrate()` call without `max_batch`, and how to skip it (pass `max_batch`, or `same_f=True`). When it ends, a warning reports the time taken, why the search stopped, the bytes per evaluation, and the `max_batch` the memory usable at that moment allows for the current `take_gradient`, to pass as `max_batch` in later runs. Both are logged at WARNING level, so they are silent if your application configures logging above WARNING.
- **The two split evaluation handlers share one batch loop.** `_evaluate_f_on_split_nodes` and `_evaluate_f_on_split_residual_nodes` carried byte-identical copies of the batched `f` evaluation loop with its out-of-memory retry; both now call `_evaluate_f_in_batches`. The memory cleanup after an out-of-memory error or a memory benchmark is one method, `_release_memory`, which empties the CUDA cache only on a CUDA solver (previously it did so whenever any GPU was visible, even for a CPU solver). Dead commented-out code in the residual handler and in `integrate()` was removed. No change in results.
- **Memory management moved to `padaquad/quadrature/memory.py`.** The memory benchmark, the free-memory queries, the batch-size budget (`get_max_batch`, `_get_max_f_evals`) and `_is_out_of_memory` now live in a `_MemoryManagement` mixin that `AdaptiveQuadrature` inherits, so every method is still available on the solver. The benchmark is split into `_setup_memory_checks` (the search and its stop rules), `_peak_memory_reader` (how memory is measured on each device) and `_measure_call` (one test call), with comments explaining each step. No change in results.
- **`same_f` replaces integrand matching by `id(f)`.** The solver used to remember `id(f)` of the last converged call and, on a match, reuse the stored `max_batch` (skipping the memory benchmark); ids are unreliable (a freed id is reused, and closures and bound methods get a new id on every call). The caller now says so with `integrate(..., same_f=True)`: the mesh and `max_batch` stored by the last call that returned replace the caller's `mesh` / `max_batch`, and the benchmark is skipped. With nothing stored (first call) the caller's values or the defaults are used. Both values are written together by every call that returns (converged, or stopped by `max_path_change`, which now stores the mesh it stopped on with that batch's failing steps split, and returns it as `mesh_optimal`, so the next call refines further instead of starting from, and stopping on, the same mesh) and never by a call that raises; `previous_max_batch` therefore holds the `max_batch` of the last returning call, not of the last evaluation. Without `same_f=True` or `max_batch`, the memory benchmark now runs on every call.
- **`max_path_change` measures the whole starting mesh.** It used the fraction of failing steps in each batch, so the two halves of one split step could end a call early, and a rough region in the first batch could end it even when the rest of the mesh passed. It now counts the failing steps of the starting mesh across all batches (split halves are not counted) against the starting step count, and stops as soon as that fraction reaches `max_path_change`. It also runs on the stored mesh used by `same_f=True` (`reuse_mesh=True` never ran it on the cached mesh), never on a freshly generated mesh.
- **The mesh-merging cutoff accounts for how a step's error grows when two steps merge.** `mesh_optimal` merged a pair of steps when their summed error ratio S was below `remove_cut`, without evaluating the merged step. A merged step of width 2h has an error of about 2^(k-1)·S when the method's error estimate scales as h^k, so 7–22 % of those merged steps failed when the same integrand was re-evaluated on `mesh_optimal` (dopri5, gk7, cc17 in our tests). A pair now merges only when S < `remove_cut` / 2^(k-1), so the merged step's predicted ratio stays below `remove_cut`; none failed in the same tests. Each method carries k as `error_exponent` (2 for adaptive Heun and fehlberg2, 3 for bosh3, 5 for dopri5, 7/15/21/31 for gk7–gk31, 5/7/11/19/35 for cc5–cc65, and 3 for `interpolatory3_variable`). `mesh_optimal` is larger in 150 of the 390 snapshot cases (up to 75 %, 8 → 14 barriers for cc17 on `damped_sine` at the tight tolerance); integrals are unchanged, because merging happens only after convergence. For high-order methods at tight tolerances, or in float32, the error estimate is round-off, which does not shrink as h^k, so few pairs reach the cutoff: from a 512-step start on smooth integrands, 8 repeated `same_f=True` calls leave gk31 at 7–30 steps and cc65 at 74–264, where gk21 reaches 2–4.
- **`get_max_batch()` defaults to the solver's `total_mem_usage`** instead of a second, fixed default of 0.9.

### Removed

- **`integrate(reuse_mesh=...)` and the `previous_f_id` attribute.** Use `same_f=True`. Migration: with `reuse_mesh=True` an explicit `mesh` won over the cached one; with `same_f=True` the stored mesh and `max_batch` replace the caller's. `same_f` takes `reuse_mesh`'s position, so a positional `reuse_mesh` argument now sets `same_f`.
- **The `device_type` and `device_ids` solver attributes.** Use `solver.device` (a `torch.device`) instead.

### Fixed

- **Cumulative error mode merged steps that failed when re-evaluated.** With `use_absolute_error_ratio=False`, the summed error ratio of a pair of steps (used only to build `mesh_optimal`) was divided by the tolerance of the larger of the two running integrals, `max(|cum_i|, |cum_{i+1}|)`. The merged step ends where step i+1 ends, so it is judged against `|cum_{i+1}|`; where the running integral falls toward zero (e.g. `cos(2πt)` near `t = 1`), merged steps of `mesh_optimal` had error ratios up to 11 when re-evaluated. The pair now uses step i+1's tolerance in both error-norm families. Absolute mode (the default) and all integrals are unchanged.
- **The out-of-memory batch reduction crashed on the first out-of-memory error.** The retry path in the split evaluation handlers computed `torch.int(torch.round(0.75 * self._oom_max_batch))`: `_oom_max_batch` starts as `None`, so the first out-of-memory error raised `TypeError` instead of shrinking the batch, and `torch.int` is a dtype, not a function. The batch is now seeded from the live `max_batch` and shrunk with `max(1, min(round(0.75 * prev), prev - 1))`, which strictly decreases (`round(0.75 * 2) == 2` would retry forever). This path had no tests; `tests/test_oom_recovery.py` now covers it with a simulated out-of-memory integrand.
- **CPU and CUDA-library out-of-memory errors are recognized.** A refused CPU allocation raises a plain `RuntimeError` naming `DefaultCPUAllocator`, numpy raises `MemoryError`, a failed `cudaMalloc` outside PyTorch's allocator raises "CUDA error: out of memory", and CUDA libraries report their own allocation statuses (`CUBLAS_STATUS_ALLOC_FAILED` and the cuSOLVER, cuSPARSE, cuFFT and cuDNN equivalents); none of these is a `torch.OutOfMemoryError`, so the batch loop and the benchmark crashed instead of shrinking the batch. They are now handled the same way. Any other `RuntimeError` from `f` still propagates unchanged.
- **Callers can choose the device, including the GPU index.** `device="cuda:1"` raised `ValueError` and a `torch.device` raised `AttributeError`, so every solver ran on `cuda:0` (or `cuda:<local_rank>` when distributed). `device` now accepts `"cpu"`, `"cuda"`, `"cuda:N"`, a `torch.device`, or `None` (auto-detect), both on the solver and in the `padaquad.integrate()` wrapper. One normalizer, `_resolve_device`, handles `device` and `result_device` and raises `ValueError` for an unsupported type, unavailable CUDA, a GPU index that is not visible, or (distributed only) an explicit index that differs from the rank's GPU. For `result_device`, an index-less `"cuda"` means the solver's GPU and `None` keeps results on the solver's device.
- **Cross-device crash in the accepted-panel re-check.** When `result_device` differed from the integration device, removing a re-split panel rebuilt the recorded `loss` on the integration device while new batches were recorded on `result_device`, so the next recorded batch raised a cross-device addition error. The loss now stays on its own device.
- **The integrand check call now passes `t` shaped `[1, T]` for any number of time coordinates `T`.** Before integrating, `integrate()` calls `f` once on the lower bound to check its output. That point was built with `torch.tensor([[mesh_init]])`, which only works when `mesh_init` holds one number (`T = 1`) and raises `ValueError: only one element tensors can be converted to Python scalars` for `T > 1`. It is now `mesh_init.reshape(1, -1)`. No user could reach the old failure: `T > 1` is still stopped earlier by the `mesh_init < mesh_final` check in `_setup_integral_bounds`, so `T > 1` integration remains unsupported end to end. For `T = 1` the shape (`[1, 1]`) is unchanged. The check call now receives the caller's own bound tensor instead of a detached copy, so an `f` that modifies `t` in place would change the caller's `mesh_init`; such an `f` already fails inside the solver, which also passes `f` views of its node array.

## [1.2.2] - 2026-06-22

### Changed

- **The per-evaluation memory benchmark (`_setup_memory_checks`) was rewritten to be stable and self-limiting.** It now grows the probe batch by powers of ten until the integrand either takes measurably long (`eval_time > 0.1s`), overshoots available memory, or reaches the `1e9` search ceiling, and derives `f_unit_mem_size` from the usable-memory budget at that point. The result is floored so the implied `max_batch` never extrapolates past the largest tile actually validated — previously the time-based branch could imply a `max_batch` ~100× the tested size and risk an out-of-memory error on the first real batch. On an out-of-memory event during the probe the batch is backed off (`0.75 * N`) and retried instead of aborting, and the benchmark now honors the caller's `total_mem_usage` fraction. It logs a warning when it runs (it is slow if repeated) and reports the resolved `max_batch` on completion.

### Added

- **`get_max_batch(total_mem_usage=0.9, default_max_batch=None)`** on the solver: resolves the per-batch evaluation cap *without* re-benchmarking memory. Precedence is an explicit `default_max_batch` (e.g. a per-call `max_batch`), then the construction-time `init_max_batch`, then the budget implied by a prior memory benchmark (`f_unit_mem_size`), all clamped by any `_oom_max_batch` discovered after an out-of-memory event. This lets calling code capture `max_batch` after a first run and feed it back into later solvers/calls to skip the slow benchmark.

## [1.2.1] - 2026-06-16

### Changed

- **Accepted integration panels are now re-validated against the drifting error tolerance.** In absolute-error mode the accept/reject denominator (`max(atol, rtol * |I|)`) depends on the running integral, which changes as more panels are evaluated — so a panel accepted early could later violate the *current* tolerance yet remain accepted, silently breaking the error guarantee. Each iteration the solver now re-checks every already-accepted (recorded) panel against the same `reference_integral` the current batch uses; any that now fail are removed from the record and bisected in the same mesh update (`_adaptively_increase_mesh` gained an internal `extra_split_idxs` argument), and their refined children are re-evaluated. At convergence **every** recorded panel satisfies the final tolerance. Runs only on the `take_gradient=False` path (where no per-batch backward can be double-counted and the full-integral denominator is available) and is skipped when a fixed `error_integral_reference` pins the denominator. The `take_gradient=True` path is unchanged. **This can change the converged mesh and integral** for multi-batch, drifting-denominator integrands (notably cancelling ones, where the denominator collapses toward `atol` as the integral cancels).
- **Snapshot golden values are keyed per `take_gradient` mode and regenerated.** The two modes legitimately diverge once the re-check engages (they only ever coincided when every panel fit in a single batch); `take_gradient=True` values are unchanged.

### Fixed

- **Default-loss detection in the record bookkeeping** compared bound methods by identity (`loss_fxn is self._integral_loss`), but `obj.m is obj.m` is `False` for bound methods, so the recorded `loss` was never rebuilt after a panel removal. It now compares the underlying function; a custom `loss_fxn` is still left as-is.
- **`_rec_remove` recursion overflow.** The post-convergence prune helper was tail-recursive and hit Python's recursion limit on the large, finely-refined meshes the re-check produces for cancelling integrands at tight `atol`. Converted to an equivalent `while` loop — identical output (snapshots unaffected), no depth limit.

## [1.2.0] - 2026-06-14

### Changed

- **Error tolerance is now computed against the complete integral (notable for memory-heavy integrands).** The `take_gradient=False` evaluation path (`_evaluate_f_on_split_nodes`) now evaluates *every* pending panel in a single pass before any accept/reject decision, so the integral is complete the first time a panel is judged. The absolute-mode tolerance denominator (`max(atol, rtol * |I|)`) therefore uses the full integral from the start, instead of the running (incomplete) integral that accumulated batch by batch. This yields better mesh-split decisions, but **can change integration results for integrals large enough to span multiple batches** (`total_nodes > max_batch`): the early panels are now judged against the true total rather than a too-small partial sum, so the converged mesh and integral can differ from prior versions. Small integrals that fit in one batch are unaffected. `max_batch` continues to bound memory by chunking the `f` calls; it no longer fragments the error decision.

### Added

- **`conserve_memory`** argument on `integrate()` (and the public `integrate()` wrapper), default `False`. When `True`, the solver uses the previous memory-conserving path (`_evaluate_f_on_split_residual_nodes`): it evaluates a bounded number of panels per loop iteration and carries a partial-panel residual forward across iterations, so peak memory is bounded by `max_batch` rather than by the whole mesh. This restores the pre-1.2.0 incremental behavior (and the running-integral error denominator it implies). Use it when the full set of node evaluations does not fit in memory.

### Fixed

- **Bug:** `_evaluate_f_on_split_nodes` iterated an undefined `tracked_list` (instead of `tracked_lists`) when concatenating tracked variables across batches, raising `NameError` whenever an integrand emitted tracked variables on the default path.

## [1.1.1] - 2026-06-13

### Added

- **`result_device`** argument on `integrate()` (and the public `integrate()` wrapper), default `'cpu'`: the large per-step records (`nodes`, `y`, `h`, `mesh_quadrature_errors`, `error_ratios`, `integral_error`, `loss`, `tracked_variables`) are detached and moved to `result_device` as they are recorded, so they no longer accumulate on the integration device. This bounds GPU memory on fine meshes — previously the full record grew on the GPU for the entire run even though most fields are only needed in the returned result. The two fields read back inside the loop (`integral` and `mesh_quadratures`) stay on the integration device. When `take_gradient=False` the autograd graph is retained across the device move, so the returned integral remains differentiable (gradients flow back to parameters on the integration device).

### Changed

- **Record ordering is now by mesh position (robust to vector-valued time).** Recorded panels are merged/sorted by each panel's position in the mesh (its left barrier looked up in a `mesh_indices` map) instead of by the first node's first time-coordinate. The previous coordinate-0 key is not a valid total order when `t` is a vector (`T > 1`, e.g. path integrals) and could misorder the record; the mesh order is correct for any `T`. For scalar time (`T == 1`) the order is unchanged and results are byte-identical (snapshots unaffected).
- **Default result device (notable for CUDA users):** with `result_device` defaulting to `'cpu'`, `integrate()` now returns the large result tensors on CPU by default; pass `result_device='cuda'` (or your device) to keep them on the GPU. The "mesh family" (`mesh_optimal`, `mesh_init`, `mesh_final`) always stays on the integration device because `mesh_optimal` is the warm-start mesh fed back into the solver and its endpoints are `mesh_init`/`mesh_final`. On a CPU-only solver `result_device` is a no-op.
- **Device-consistent internals:** the error-ratio helpers and adaptive-mesh refinement (`_adaptively_increase_mesh`, `_get_optimal_mesh`) are now device-following (tolerances and allocations follow their inputs), and the merge/sort paths place index tensors on each field's device, so a record split across devices stays consistent.
- **Coordinate-0 assumptions removed for multi-dimensional `t`:** post-refinement/record monotonicity assertions are reframed (the 1-D strictly-ascending checks are retained, guarded to `T == 1`), initial sub-barriers are generated along the segment vector, and the `reuse_mesh` warm-start filter uses an all-coordinate bounding box instead of a coordinate-0 range.

### Fixed

- The `max_path_change` early-exit `IntegrationResult` is now device-consistent with the normal-completion path.

### Removed

- Internal `_get_sorted_indices` (coordinate-based binary-search merge), superseded by mesh-position placement (`_mesh_order` + `_merge_positions`).

## [1.1.0] - 2026-06-09

### Added

- **`error_integral_reference`** argument on `integrate()`: in absolute-error mode the rtol denominator is the running (incomplete) integral, which over-refines early panels when the integrand's mass is concentrated at later times. This argument accepts a Python float or tensor close to the true total, using it as the denominator from the first batch onward. Has no effect in cumulative mode.
- **`error_norm`** argument (constructor + per-call override): pluggable vector-error norm schemes replacing the fixed RMS reduction, modeled on `scipy.integrate.quad_vec`'s `norm`:
  - Norm family (`"2"` default, `"max"`, `"rms"`, or a callable) — reduce-then-compare: collapse the error vector with the named norm, compare to the tolerance.
  - `"failure_fraction"` — per-component control: each output element is compared against its own tolerance; a panel is accepted when the fraction of failing elements is ≤ `mesh_failure_tolerance` (default `0.0`, requiring every element to pass).
- **Rounding floor** (`max(tol, 50 * eps * |step|)`): refinement halts at the working-dtype precision wall instead of refining indefinitely when the requested tolerance is below the dtype's resolution.
- **`error_on_nonfinite`** flag (default `True`): raises a `ValueError` naming the offending `t` when `f` returns NaN/Inf, preventing silent wrong results.
- **`max_adaptive_splits`**: configurable ceiling on adaptive refinement depth (added in v1.0.2; documented here for completeness).

### Changed

- **Error tolerance formula (breaking for fine tolerances):** the accept/reject threshold for the norm family has changed from `atol + rtol * |I|` (additive) to `max(atol, rtol * |I|)` (maximum), aligning with `scipy.integrate`. This tightens tolerance when both terms are comparable; snapshot values have been regenerated. The `failure_fraction` scheme retains the additive form.
- `atol` and `rtol` are now stored as dtype-aware tensors in `SolverBase` and re-cast in `_set_dtype`.
- `y0`, `mesh_init`, and `mesh_final` defaults now honor the solver's dtype rather than hard-coding float64.
- `max_batch < C` (`take_gradient=False`): sub-panel batch budgets are now supported. The split path processes one panel per iteration, evaluating its `C` nodes across several `max_batch`-sized sub-batches and carrying remainders forward. The final integral is bit-identical to a `max_batch ≥ C` run with the same seeded mesh. `max_batch == 0` at the dispatcher is rescued to `1` (with a warning); a direct unit call to `_evaluate_f_on_split_nodes` raises `AssertionError`. `take_gradient=True` below `C` continues to raise an error.
- Non-finite error ratios (from singular integrands) are routed into the accept mask rather than hanging the refinement loop indefinitely.
- GPU device handling: user-provided meshes, `f_args` tensors, and internal assertions are now consistently placed on `self.device`, fixing 850 test failures on CUDA machines.
- `max_batch` is cached between calls when `f` is the same function, avoiding a full re-benchmark on every `integrate()` call.
- Out-of-memory errors during integration and memory benchmarking are caught; `max_batch` is lowered and the evaluation retried.

### Fixed

- **Bug:** the integral loss was computed as `sum(step²)` instead of `(integral)²`.
- **Bug:** misplaced parenthesis in the tolerance expression.
- **Bug:** `VariableAdaptiveQuadrature` did not call `method.to_device(self.device)` at construction, leaving method tensors on CPU when the solver was on CUDA.
- **Bug:** `_merge_excess_nodes` used `np.allclose` for a device-agnostic sanity check, which fails on CUDA tensors; replaced with `torch.allclose`.
- **Bug:** non-finite error ratios caused an infinite adaptive refinement loop.

### Removed

- `error_calc_idx` argument (superseded by the callable form of `error_norm`).

## [1.0.0] - 2026-05-30

First stable release. The project, formerly `torchpathdiffeq` (an ODE / path-integral library), has been rebuilt and renamed to **`padaquad`**, a PyTorch library for **parallelized adaptive numerical quadrature**: it computes definite integrals $\int_a^b f(t)\,dt$ for a known integrand `f` by evaluating many quadrature panels in parallel batches on GPU/CPU, with full autograd through the integration loop.

The integrand `f` depends only on `t` (and optional extra args), **not** on accumulated state `y`. This is numerical quadrature, not ODE solving — for state-coupled $\dot y = f(t, y)$ use `torchdiffeq` / `torchode` / `diffrax`.

### Added

- Parallel, memory-aware batched evaluation: quadrature panels are evaluated in batches sized automatically to the available GPU/CPU memory budget.
- Adaptive mesh refinement: panels that miss tolerance are split at their midpoint and re-evaluated; over-resolved regions are merged. The converged mesh can be cached and warm-started (`reuse_mesh=True`) for repeated calls on the same integrand.
- Method portfolio (default `gk21`):
  - Gauss–Kronrod: `gk7`, `gk15`, `gk21`, `gk31`
  - Clenshaw–Curtis: `cc5`, `cc9`, `cc17`, `cc33`, `cc65`
  - Runge–Kutta baselines: `adaptive_heun`, `fehlberg2`, `bosh3`, `dopri5`
  - Variable-sampling rules: `adaptive_heun`, `interpolatory3_variable`
- Uniform and variable sampling modes (fixed tableau-`c` node positions, or arbitrary node positions with weights computed dynamically).
- Full autograd through integration, including a memory-frugal per-batch-backward mode (`take_gradient`) for training learnable integrands whose full graph would not fit in memory.
- `y0` additive offset (`result.integral = y0 + ∫f`) and positional `f_args` forwarding to `f(t, *f_args)`.
- Public API: `integrate`, `adaptive_quadrature`, `UniformAdaptiveQuadrature`, `VariableAdaptiveQuadrature`, `IntegrationResult`, `UNIFORM_METHODS`, `VARIABLE_METHODS`, `integrand_dict`, `wolf_schlegel`, `steps`.

### Changed

- **Renamed package `torchpathdiffeq` → `padaquad`.** Update imports accordingly (`from padaquad import ...`).
- Reframed the public API around quadrature: `IntegrationResult` exposes integral- and mesh-oriented fields (`integral`, `integral_error`, `nodes`, `mesh_optimal`, `mesh_init`, `mesh_final`, `mesh_quadratures`, `mesh_quadrature_errors`, `error_ratios`, …).
- `float64` and `float32` are the supported runtime dtypes; `float16` is refused at construction.

### Removed

- ODE-centric framing and semantics. `padaquad` does not integrate state-coupled ODEs; use a dedicated ODE library for those.
